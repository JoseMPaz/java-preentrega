\section{Introducción y Arquitectura del Sistema}
El presente proyecto documenta la preentrega de la plataforma de control de inventario de TechLab. El software se modeló utilizando el paradigma de Programación Orientada a Objetos (POO) bajo una arquitectura desacoplada en capas. Este enfoque asegura un diseño de software mantenible y modular, aislando la lógica transaccional de los mecanismos de presentación.

\subsection{Distribución Modular de Responsabilidades}
La separación de paquetes encarna el principio de Cohesión y Responsabilidad Única (SRP):
\begin{itemize}
    \item \textbf{model:} Contiene las entidades puras del negocio (POJOs), responsables de modelar el estado del objeto.
    \item \textbf{service:} Capa lógica central encargada de las transacciones CRUD y la manipulación de la persistencia volátil en memoria.
    \item \textbf{exception:} Centralización funcional de los errores de negocio mapeados mediante excepciones personalizadas.
    \item \textbf{ui:} Gestión del flujo de consola y entrada/salida interactiva de datos.
    \item \textbf{util:} Módulos utilitarias estáticos para el procesamiento genérico y la sanitización de entradas por teclado.
\end{itemize}

\subsection{Patrón de Inyección de Dependencias}
Para evitar el acoplamiento duro, se implementó el patrón de Inyección de Dependencias por Constructor dentro de la clase \texttt{MenuProducto}. Al recibir el Scanner y la instancia de \texttt{ProductoService} desde el exterior, la interfaz queda desacoplada de la inicialización de sus componentes. Esta práctica es la base técnica fundamental para la futura migración hacia frameworks empresariales como Spring Boot.

\section{Pruebas Unitarias}

Las pruebas unitarias implementadas en este proyecto se enfocaron exclusivamente en el modulo ProductoService debido a que este componente constituye el núcleo de la lógica de negocio del sistema. En una arquitectura de software limpia y distribuida por capas, es fundamental garantizar la estabilidad y el correcto comportamiento de la capa de servicio de manera aislada.

Este enfoque selectivo se justifica por las siguientes razones de ingenieria de software:

\begin{itemize}
    \item \textbf{Aislamiento de la Logica de Negocio:} Las clases pertenecientes al paquete model solo actuan como contenedores de datos (POJOs), mientras que las utilidades del paquete util y las excepciones son componentes de soporte. ProductoService es el unico modulo que procesa, altera y valida las reglas del negocio.
    \item \textbf{Desacoplamiento de la Interfaz:} El paquete ui (MenuProducto) y la clase Main se encargan unicamente de la interaccion con el usuario a traves de la consola. Probar esos modulos requeriría simular entradas de teclado (Scanner) y flujos de salida (System.out), lo cual pertenece al ambito de las pruebas de integracion o de interfaz, no a las pruebas unitarias.
    \item \textbf{Validacion de Flujos Criticos:} Al concentrar los esfuerzos en este servicio, se logro verificar de forma automatizada tanto los casos de exito del CRUD como la correcta respuesta del sistema ante fallos, forzando de manera segura el lanzamiento de las excepciones ProductoNoEncontradoException y StockInsuficienteException.
\end{itemize}

\subsection{Estrategia de Testing y Robustez del Dominio}
Para asegurar la estabilidad matemática del software, se incorporaron técnicas avanzadas de control de estado en la suite de pruebas unitarias:
\begin{itemize}
\item \textbf{Mecánica Fail-Fast:} Los métodos de prueba evalúan que los validadores lancen excepciones de manera inmediata (\texttt{IllegalArgumentException}) ante cargas de datos corruptas o inconsistentes (ej. nombres vacíos o precios negativos), protegiendo la integridad del catálogo en memoria.
\item \textbf{Control de Estado Estático:} Debido a que la capa de servicio utiliza un contador estático secuencial para la asignación de llaves primarias (IDs), se diseñó un método utilitario \texttt{reiniciarServicio()} invocado en el ciclo \texttt{@BeforeEach}. Esto limpia la colección y resetea el puntero a 1 antes de cada test, garantizando el principio de Independencia Funcional (las pruebas no se contaminan entre sí).
\end{itemize}

\section{Conclusiones}
La resolución de esta preentrega mediante la consola de Linux consolida un backend sólido y resiliente. El uso de validaciones defensivas blindadas contra el desbordamiento de búfer del \texttt{Scanner} asegura una experiencia estable para el usuario. El éxito en la ejecución de la suite de JUnit 5 valida matemáticamente el comportamiento del CRUD y el control de errores, dejando el ecosistema de TechLab con bases arquitectónicas profesionales y listo para su futura integración con sistemas de bases de datos relacionales persistentes.
